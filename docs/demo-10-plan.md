This plan applies the lessons from demos 5–9:

1. **Preflight calibration is a task, and the pilot may kill the demo — not just reframe it.** Demo 10's viability gate is harder than any predecessor's: the CCX block structure must be *visible and stable* through WSL2's vCPU→pCPU mapping before anything is briefed. The rig itself is under test here, not just the thesis. A uniform or noisy pilot matrix stops the demo (§1/A1).
2. **Capture environment is explicit — and this demo is inherently multi-core.** It cannot run on "a single isolated core": each measurement pins two threads to a pair drawn from the isolated set, with the orchestrator kept off it. Demos 2 and 4 established the multi-thread-pinned precedent on this rig; the brief states the departure from the single-core convention rather than assuming it.
3. **Fine-structure claims require multi-capture support** (demos 05–08 rule). A matrix *invites* readers to see fine structure — pair-to-pair variation inside a block is exactly the kind of claim that needs corroboration. Two independent captures are baked into §6 by default; they cost minutes.
4. **Harness-emitted strings are fixed at source** (demo 9's `cores_physical` / `notes` lesson). Machine block and notes come from code, never hand-edits, so recaptures can't silently regress them.

## Story angle (provisional — pilot confirms)

**Headline — the topology made visible.** Pinning threads is table stakes; *which cores you pin to* is a topology decision, and on Matisse the topology has a seam. Cores in the same CCX exchange a cache line through their shared L3 slice; cores in different CCXs exchange it via the IO die over Infinity Fabric, despite sitting millimetres apart. The post measures pairwise round-trip latency for every core pair in the isolated set and renders the matrix as a heatmap. Prediction stated up front, demo-3 style: two tight intra-CCX blocks in one band, a cross-CCX block sitting a multiple higher, the boundary legible at a glance. **Magnitudes are deliberately not pre-committed** — they're rig-specific (FCLK-dependent, and virtualised); the pilot records what this machine gives and the post reports it, including if the gap is smaller or stranger than folklore suggests. Surprising results are findings.

**Secondary — the exhibit the earlier posts have been pointing at.** Demos 2, 4, and 5 each carry cross-CCX caveats or companion measurements (penalty-magnitude framing in demo 2, producer/consumer placement in demo 4's tail, demo 5's cross-CCX companion capture). Demo 10 unifies those scattered sentences into one definitive chart — and the reconciliation runs both ways: the matrix must be consistent with what those posts already claim (re-derived from their committed JSON, per §1/A5), and they gain a link target in return.

**What the post does NOT claim:** that this is NUMA — it's one memory domain; the finding is *coherence topology*, not memory locality, and the distinction is named because readers conflate them. That this generalises across AMD — it's Matisse-specific; Zen 3 unified the eight-core CCX and dissolved this boundary on 8-core parts, so the post is microarchitecture anatomy, not vendor scorekeeping. That the absolute nanosecond values are bare-metal truth — WSL2 sits under everything, so the robust claims are the **block structure and the intra/cross ratio**, with absolute values reported under an explicit hypervisor caveat (the demo-9 discipline: name the portable quantity). And the RTT convention is explicit: the post reports what is measured (a round trip), names the common halve-it convention, and never silently halves.

## Lessons from demos 5–9 applied to this plan

- **The pilot can kill, not just reframe.** A1 tests the rig (WSL2 mapping stability), not merely the thesis — the strongest form of pilot-before-brief so far. The teaser waits accordingly.
- **Multi-capture is designed in, not retrofitted.** Two captures at §6 because a matrix invites exactly the fine-structure reading the demos 05–08 rule exists for.
- **Reconciliation targets come from the repo.** A5 inventories the live cross-CCX claims by grep and re-derives their figures from committed JSON — never from memory or stale snapshots, the failure mode that produced inverted verdicts before.
- **Harness strings fixed at source.** Demo 9's `cores_physical` / `notes` regression class is closed by construction here.
- **New component only where composition can't express it.** The heatmap qualifies; every supporting view reuses.
- **The multi-core departure has precedent and is stated.** Demos 2 and 4 already pinned thread pairs on this rig; the brief names the convention change instead of assuming it.
- **Let the data assign the labels.** CCX membership of guest core indices is read off the pilot matrix blocks, not asserted from host-side assumptions filtered through a hypervisor.
- **No brief-format change.** The demo 7/8/9 shape carries over.

## Open items (to be resolved during §1 / §2)

- **Slug and title.** Default slug `10-core-to-core`; title candidates "Anatomy of the CCX" / "The Seam in the Silicon". Editorial.
- **A2 — protocol.** Default: atomic-exchange ping-pong on a single `alignas(64)` line (simplest inner loop to show in the post); the two-line flag handshake measured once in the pilot for the record, with the coherence-traffic difference documented whichever way it goes.
- **Memory-ordering axis.** seq_cst vs acquire/release as a second variant dimension would be a different post. Default: acquire/release throughout, one sentence in the post naming the choice; the ordering comparison is a possible future demo, not this one.
- **A4 — core 0.** Default: exclude. That yields a 7-core matrix with asymmetric CCX membership (expected three cores from one CCX, four from the other — exact grouping read off the data per A1); the asymmetry is stated in the post. If the measured-with-caveat row turns out interesting (housekeeping noise as a visible stripe), including it is an editorial option.
- **RTT vs one-way.** Default: report measured RTT, name the RTT/2 convention, never silently halve. Locked unless §1 surfaces a reason to revisit.
- **Schema representation of pairwise data.** The locked `runs[]` per-variant shape doesn't naturally express a matrix. Options: one variant per pair (`pair_1_4`, … — 21 entries, verbose but schema-conformant) vs a demo-local extension block (demo 4's sweep and demo 5's pressure data are precedent). Decide in §2 with the chart loader in view; the machine-block / `captured_at` contract is untouchable either way.
- **Second-capture placement.** Where the corroborating capture lives and how the post cites it — follow whatever the demos 05–08 exhibits established; confirm the pattern from the repo at §2 time rather than restating it here.
- **Heatmap rendering.** Full symmetric square (easier to read at a glance) vs lower triangle (honest about symmetry, denser). §5 decides with the mobile constraint in view.
- **Expected magnitudes.** Deliberately unpinned. The pilot records this rig's numbers; the post states the structural prediction (two bands, cross ≫ intra) and reports what the hardware gave. If the gap underwhelms or the blocks show unexpected structure, that is the finding — demos 5 and 7 are the precedent for rescoping around reality.
- **WSL2 framing depth.** One caveat sentence vs a short section. If A1 shows any instability worth discussing, the virtualisation story may earn a section of its own; editorial after the pilot.
