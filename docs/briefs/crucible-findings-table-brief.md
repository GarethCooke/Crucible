# Brief: "At a glance" findings table on the homepage

Branch: `feat/findings-table`
Base: `master` @ `ab75a9c`

## Context

The homepage (`site/src/app/page.tsx`) lists the ten posts as title and summary only. We are adding an **"At a glance"** section **above the Posts list**. It is a table with one row per numbered demo (01–10) and shows what each post is about and what it measured.

Decisions already made (do not reopen):

- It goes on the homepage, above `Posts`.
- Columns: **#**, **Topic** (name plus a one-line plain-English "what it is"), **Headline**, **Measured at**, **Finding**.
- Headline figures come **from JSON at build time**. No measured number is typed into TSX, MDX or any prose field.
- The quantum special edition is **excluded**.

Design choice made in this brief: headline specs live in **sidecar files** `site/src/data/perf/NN-*.headline.json`, not inside the capture JSON. The capture JSON is regenerated by `bench/scripts/assemble_results*.py`, which would clobber a hand-added block. Sidecars follow the existing `10-core-to-core.protocol.json` / `.slice-sweep.json` precedent. A sidecar holds a *selector* into the capture JSON, and the build computes the figure from it. Recaptures therefore flow into the table automatically.

### Task 1 — Sidecar schema and types

Add these types to `site/src/lib/perf-types.ts`:

```ts
export interface RunSelector {
  /** Dotted path to the array to search. Default "runs". */
  collection?: string
  /** Exact-match filter on keys of each element. */
  where: Record<string, string | number | boolean>
  /** Dotted path to a numeric leaf, e.g. "ns_per_op.median". */
  field: string
  /** "single" (default): exactly one match is required, else throw.
   *  "median": the median of the field across all matches (>= 1 required). */
  aggregate?: 'single' | 'median'
}

export type Headline =
  | { kind: 'ratio'; source: string; numerator: RunSelector; denominator: RunSelector; decimals: number; suffix: string }
  | { kind: 'text'; text: string }

export interface HeadlineSpec {
  slug: string          // post slug, e.g. "02-false-sharing"
  topic: string
  what_it_is: string
  headline: Headline
  condition: string
  finding: string
}
```

`source` is the capture JSON basename without `.json`. This is often **not** the post slug; for example, `02-false-sharing` reads `02-false-sharing-pnl`.

Editorial text (verbatim):

| # | topic | what_it_is | condition | finding |
|---|---|---|---|---|
| 01 | Branch prediction | The CPU guesses which way an `if` goes before it knows; a wrong guess throws away work already in flight. | N = 32 M, unsorted vs sorted | Unpredictable branches, not the work, dominate the loop — and branchless code recovers most of the gap without sorting. |
| 02 | False sharing | Two threads write different variables that happen to share one 64-byte cache line, so the line ping-pongs between cores. | 8 threads across both CCXs, unpadded vs padded | Padding each accumulator onto its own cache line is the whole fix: layout beats algorithm. |
| 03 | SIMD | One instruction operates on several values at once, using wide vector registers. | 1 M options, scalar libm vs AVX2+FMA | A polynomial erfc barely helps on its own, but it unlocks vectorisation that libm can't reach. |
| 04 | Lock-free queues | Passing messages between threads with atomic operations instead of a lock that can put a thread to sleep. | p99.9 at 1 MHz offered load, mutex vs lock-free | Mutex latency is thread wake-ups; lock-free keeps the tail tight. |
| 05 | Allocators | Where `new` gets its memory; custom pools avoid the general-purpose heap's locking and bookkeeping. | freelist vs arena vs new/delete, two captures | Neither pool reproducibly beats the other; both beat new/delete on the tail, and the arena's tail stays flat under pressure. |
| 06 | Data layout (AoS vs SoA) | Storing each record's fields together (array of structs) versus each field in its own array (struct of arrays). | N = 1 M, one hot field, AoS vs SoA | SoA wins only when few fields are hot and the data spills past L3. |
| 07 | Hash maps vs flat maps | Choosing a key→value container: node-based tree, sorted vector, or open-addressing hash table. | N = 8 to ~4 M, lookup and modify mixes | absl::flat_hash_map is fastest at every size; the expected small-N crossover never appears. |
| 08 | Sorting | Comparison sorts can't beat n log n; radix sort sidesteps that by bucketing integer keys a byte at a time. | 67 M random u32 keys, std::sort vs radix | On narrow integer keys radix wins, and its cost doesn't depend on input order. |
| 09 | ARM NEON | ARM's 128-bit SIMD instruction set, running the demo 03 kernel on a Raspberry Pi 5. | 1 M options, scalar poly vs NEON | The speedup is capped by vector width; there's no wider unit to reach for. |
| 10 | Core-to-core latency | How long one core takes to see a cache line another core has just written. | median cross-CCX vs same-CCX round trip | Crossing the CCX boundary taxes every handoff; pin chatty threads within one CCX. |
